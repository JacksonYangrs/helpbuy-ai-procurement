## 1. 概述

### 1.1 背景
采集层（主文档）把客户"甩"来的需求结构化沉淀为 `procurement_order` 子单，并经 AI 识别 + 人工确认进入订单池。其中 `business_type ∈ {代下单, 全包}` 的子单，最终需要在第三方电商平台（淘宝 / 京东 / 拼多多 …）完成「选品 → 填单 → 下单 → 付款」。本期要把这一段**自动化**：以「确定性浏览器脚本为主力、AI 视觉兜底、人工确认闸守关键节点」替代人工操作。

> 本章设计以 §1.4「电商平台 API 接口调研」为现实依据——各平台是否开放买家代下单 API，直接决定本子系统的通道选型（browser / official_api）。

### 1.2 目标
- 已确认子单自动在目标平台完成下单，**收货单位 = 客户**（沿用主文档 §4.3 禁止合并约束，每个子单独立下单）
- 付款使用**平台账号**（`payer_type = platform`，非客户自付）
- **全平台覆盖**：per-platform 适配器，新增平台只加一个适配器文件，引擎零改动
- 最大风险 = **平台自动化风控** → 必须有「检测 → 熔断 → 转人工 → 同浏览器续跑 / 切备用账号」的完整应急链路

### 1.3 模块边界
- **输入**：`procurement_order` 中 `status = 已确认` 且 `business_type ∈ {代下单, 全包}` 的子单
- **输出**：平台订单号、付款凭证、物流单号、状态流转（落库）
- **不处理**：
  - `business_type = 代付款`（客户已自行付给供应商，无平台下单动作）
  - `business_type = 代询价比价`（仅寻源比价，不落地单）
  - 这两类子单不会进入执行队列

---

### 1.4 电商平台 API 接口调研（设计依据）

本子系统要对接第三方电商完成「选品 / 填单 / 下单 / 付款」。能否走官方 API 直连，取决于各平台是否向**买家侧（代采方）**开放下单 / 支付接口。2026-07 调研结论如下：

| 平台 | 开放平台 | 是否提供买家代下单 API | 适用场景与对代采的含义 |
|------|---------|----------------------|----------------------|
| 京东（VOP 京东企业购） | 京东 VOP / 宙斯开放平台 | **提供（B2B 最契合）** | 100+ 标准接口、10 类采购模块；`jingdong.vop.order.submitOrder` 直接返回京东订单号；支持一单多地址、集中付款、集中开票、自动对账。代采方作为企业采购方，可官方直连下单，最稳、不被风控。 |
| 1688（阿里巴巴 B2B） | 1688 开放平台 | **提供（B2B）** | 「采购解决方案（服务商版）」面向买家采购：`alibaba.trade.fastCreateOrder` 一步创建订单，全链路含授权 / 地址 / 创建 / 免密支付 / 查询 / 撤单。适合 B2B 批发代采；需订购解决方案、有调用量门槛。 |
| 淘宝 / 天猫（TOP） | 淘宝开放平台 | **不提供（买家侧）** | 交易类 API（自动下单、支付）仅对特定 ISV 服务商 / 品牌商家开放，需企业资质 + 严格审核；普通代采方作为买家**无官方下单入口**。可调用商品查询、店铺订单查询（卖家视角）。买家代采只能走浏览器模拟，或对接已授权的商家 ERP（非买家代采）。 |
| 拼多多 | 多多开放平台 | **不提供（买家侧）** | 开放接口面向**商家 / 服务商**（订单同步、打单发货、进销存），是卖家视角；无买家代采下单 API。代采方作为买家无官方入口。 |
| 抖音电商（抖店） | 抖店开放平台 | **不提供（通用商品代采）** | 订单接口为商家视角（查询 / 发货）；「发起下单」仅限抖音小程序 / 本地生活特定业务线、需用户授权，非通用商品代采通道。 |

**调研要点**
- **B2B 平台（京东 VOP、1688）原生提供企业采购 API**，是代采最理想的程序化通道——下单 / 对账 / 开票均可官方完成，无浏览器风控之忧。这与 §12「官方 API 直连」方向完全吻合。
- **C 端平台（淘宝 / 天猫、拼多多、抖音）交易 API 仅对商家或特定合作伙伴开放**，代采方作为买家无法走官方下单；本期只能以受控浏览器（browser transport）模拟人工操作，承受平台自动化风控（见 §8）。
- **未来官方化路径**：规模化后，京东 / 1688 直接走 official_api transport；淘宝 / 拼多多 / 抖音 若要官方化，须谈 ISV / 企业购资质（门槛高、周期长），届时再扩展对应 transport。

**对设计的直接约束**
1. 本期 transport 以 `browser` 为主力，覆盖全部平台（含不开放 API 的 C 端平台）。
2. `official_api` transport 优先对接京东 VOP、1688；其 `PlatformAdapter` 实现只换底层通道，引擎 / 状态机 / 风控不变（见 §6、§12）。
3. per-platform 适配器与 transport 解耦：新增平台 = 新增适配器；新增通道（browser → official_api）= 换 transport 实现，均不侵入引擎。

## 2. 整体架构

```
[已确认子单池]                         [执行子系统 procurement_execution]
procurement_order(已确认,代下单/全包)
       │
       ▼  [引擎 engine.py]
  取子单 → 选适配器(adapter) → 打开浏览器(session)
       │
       ├─[确定性 DOM 层] Playwright 主力：登录态复用、按字段填表、稳定可重放
       │
       ├─[AI 视觉层]   兜底：动态/无稳定选择器/验证码类页面 → 视觉 LLM / computer-use 识别元素并操作
       │
       ├─[人工确认闸]  关键节点暂停（首登/付款前/风控）→ 等人工点确认或回填
       │
       └─[风控 risk.py] 检测信号 → 熔断 → status=风控待人工 → 转人工 → 续跑/切备用账号
                         │
                         ▼
                  回写 platform_order / proof_url / tracking_no → 落库
```

### 建议包结构
```
procurement_execution/
  engine.py        # 执行编排：取子单→选适配器→跑填单→风控检测→落状态
  browser.py       # 受控浏览器（Playwright）+ session 管理/复用
  ai_vision.py     # AI 视觉兜底（computer-use / 视觉 LLM，见《设计方案_代采平台AI方案.md》§6.13）
  human_gate.py    # 人工确认闸（关键节点暂停、等人工确认/回填）
  risk.py          # 风控信号检测 + 熔断决策
  payment.py       # 平台付款账号管理（主+备）+ 执行付款
  adapters/        # per-platform 适配器
    base.py        # PlatformAdapter 接口
    taobao.py
    jd.py
    pdd.py
  models.py        # execution_task 等执行子系统模型
  config.py        # 平台/账号/风控阈值配置
  tests/           # 独立测试（mock browser ctx + 沙箱真实账号）
```

**对外仅暴露**：配置加载、单子单执行、批量执行入口。其余内部实现可替换，不依赖大平台其他模块。

## 3. 执行触发与衔接

- **数据入口**：`SELECT * FROM procurement_order WHERE status='已确认' AND business_type IN ('代下单','全包')`
- **触发方式**（二选一或并存）：
  - 采集层 `pipeline.py` 在完成确认后，将子单投递到执行队列（推荐，闭环）
  - 独立命令 `python -m procurement_execution --run [--order <id>]` 手动触发（便于测试/补单）
- **调度**：执行子系统可有独立调度（如每 10 分钟扫一次待执行池），不与采集层扫描调度耦合
- **独立性**：每子单独立执行，严格沿用主文档 §4.3「禁止合并」——绝不为凑单把多个子单合并成一笔平台订单

## 4. 状态机（执行段）

复用采集层 `procurement_order.status` 字段（不新增数据库列），仅在枚举上**扩展执行相关值**。原有终态全部保留：`AI待确认 / 已确认 / 已下单 / 已付款 / 已完成 / 已取消`。

执行子系统新增枚举值（仅执行段使用）：

| 状态 | 含义 |
|------|------|
| `待执行` (queued) | 已进入执行队列，等待调度 |
| `执行中` (executing) | 浏览器已开 / 填单进行中 |
| `风控待人工` (risk_hold) | 触发风控熔断，已转人工，待运营介入 |

**流转图**
```
已确认 ──▶ 待执行 ──▶ 执行中 ──▶ 已下单 ──▶ 已付款 ──▶ 已完成
                  │           │
                  │           └──(风控信号)──▶ 风控待人工 ──┐
                  │                                         │
                  └──(可重试失败)──▶ 待执行(重试)            │
                                                            │
风控待人工 的处理出口（见 §8）：
  ├─ 同浏览器续跑：人工在已开 session 上继续 → 回 执行中
  ├─ 人工手动完成并回填 platform_order → 已下单 → 已付款 → 已完成
  └─ 切备用账号重跑未完步骤 → 执行中
任意不可恢复失败 → 已取消（保留 execution_task 记录便于复盘）
```

> **复用原则**：状态列复用、不滥加字段；每次执行尝试的明细（步骤断点、风控信号、错误、凭证）写入独立的 `execution_task` 表（类比 `ai_api_cost` 是独立成本表），核心订单表保持干净。

## 5. 执行引擎（混合架构）

执行子系统采用三层混合，按"稳的尽量确定性、不稳的才上 AI、危险的必须人把关"原则分层。

### 5.1 确定性 DOM 层（主力）
- 基于 Playwright，复用登录态（session 文件 / cookie 持久化），避免每次重登触发风控
- 按「字段名 / 选择器 / 坐标」稳定填表：商品链接、规格、数量、收货地址、发票
- 可重放、可单步调试，是首选执行路径

### 5.2 AI 视觉层（兜底）
- **定位**：确定性 DOM 层跑不通时的兜底执行路径 —— 页面动态渲染、无稳定选择器、或遇到滑块 / 简单验证码类元素时，调用**视觉 LLM / computer-use** 识别页面元素并操作（实现落在 `ai_vision.py`）
- **原则**：仅作兜底，不默认走 AI —— 确定性 DOM 能跑通就不调视觉，控成本、控不确定性；视觉动作的结果必须回到同一状态机与审计链路
- **详细方案见平台总体 AI 文档**：《设计方案_代采平台AI方案.md》**§6.13 应用场景二：下单执行（直接下单）的 AI**（触发条件、能力选型呼应其 §6.9、模型路由复用 §6.2 / §6.12、成本口径复用 §6.7、容错降级复用 §6.8）。本文档不重复展开，以 AI 文档为准。

### 5.3 人工确认闸（守关键节点）
- **首登授权**：首次在某平台启用账号，必须人工完成登录 / 验证，session 后续复用
- **付款前确认**：提交订单后的付款动作前，必须人工点确认（或配置为自动付但留审计）
- **风控转人工**：命中风控信号即暂停，转运营处理
- 人工闸是合规底线——AI 不无人监管地动钱

### 5.4 标准执行步骤模板（抽象一致，per-adapter 细节不同）
```
1. open_session()        打开/复用平台登录态
2. open_product(order)   优先用 order.product_url；无则按 item+model 搜索
3. fill_spec(order)      选规格/数量，匹配 order.model/qty/unit/spec
4. fill_address(order)   填收货地址（order.address_ref → 客户收货地址，禁止改）
5. fill_invoice(order)   填发票（customer.billing_companies / tax_id）
6. submit_order()        → 返回 platform_order_no（落 logistics_detail.platform_order）
7. detect_risk()         下单前后检测验证码/滑块/拦截页/账号警告
8. pay(account)          payer=platform，回写 payment_record.proof_url
9. sync_logistics()      物流回传后填 tracking_no
```

## 6. 平台适配器（per-platform）

新增平台零侵入：引擎只依赖接口，具体平台逻辑全在适配器文件里。

```python
# adapters/base.py（接口抽象）
class PlatformAdapter:
    name: str
    def login(self, ctx) -> None
    def open_product(self, ctx, order) -> None
    def fill_spec(self, ctx, order) -> None
    def fill_address(self, ctx, order) -> None
    def fill_invoice(self, ctx, order) -> None
    def submit_order(self, ctx) -> str          # 返回 platform_order_no
    def pay(self, ctx, account) -> str          # 返回 proof_url
    def detect_risk(self, ctx) -> "RiskSignal | None"
```

- `taobao.py` / `jd.py` / `pdd.py` 各自实现上述接口
- 各平台**风控形态不同**（滑块 / 短信验证 / 设备指纹 / 实名），`detect_risk` 由各适配器声明自身能识别的信号；`risk.py` 统一收口做熔断决策
- 新增平台 = 新增一个 `xxx.py` 实现 `PlatformAdapter`，引擎与配置零改动

## 7. 付款执行（平台账号）

- `payer_type = platform`，**付款方 = 平台账号**（客户不自付）
- 平台付款账号配置在 `platform_account`（新增配置/表），含 **主账号 + 备用账号**（可多个）
- 正常流程用主账号；触发风控熔断 / 主账号受限时，引擎切备用账号续跑（见 §8）
- 付款金额 = `order.total_amount`
- 付款凭证 `proof_url` 回写现有 `payment_record`（复用主文档 §4 表，不新建付款表）
- 单笔 / 日累计限额在 `platform_account` 配置，超限自动转人工，防资损

## 8. 风控与应急方案（最大风险）

平台自动化风控是执行子系统**最大可执行 / 合规风险**（账号封禁、资损、数据风险）。机制围绕「**不强行绕过、能续就续、不行转人、有备可切换**」。

```
detect_risk() 发现信号
      │
      ▼ 熔断（立即停止后续操作，不继续点、不继续付，防账号封禁升级）
      │
      ▼ 落状态 status = 风控待人工 + 写 execution_task(risk_signal, 断点步骤)
      │
      ▼ 转人工（通知运营，带上下文：哪个平台/哪个账号/卡在哪步/什么信号）
      │
   人工处理出口（三选一）：
   A. 同浏览器续跑：运营在已开 session 上继续操作 → engine 从断点步骤 resume，
      避免重新登录再次触发风控（保留登录态是关键）
   B. 人工手动完成：运营自己在页面点完 → 回填 platform_order_no / proof_url
      → 状态跳 已下单 → 已付款 → 已完成
   C. 切备用账号：主账号命中风控，用备用账号重新执行未完步骤
      （需登录备用账号，独立 session；execution_task 记录切换）
```

**要点**
- **同浏览器 session 续跑**：保留已登录上下文，人工介入后从断点继续，是降低二次风控的核心手段
- **切备用账号**：主账号命中风控时启用，需重新登录备用账号（独立 session），`execution_task` 记录账号切换便于审计
- **数据不丢**：`execution_task` 记录断点步骤，恢复可续、失败可复盘
- **不强行绕过**：检测到强风控（实名 / 人脸 / 法律类拦截）直接转人工，**不尝试破解、不模拟绕过**
- **可观测**：每次风控事件都落 `execution_task` + 通知，便于复盘风控规律、优化适配器

## 9. 数据模型补充

尽量复用主文档 §4 现有表，仅新增执行子系统必需表 + 扩展状态枚举。

### 9.1 复用（不新建）
- `procurement_order`：`status` 扩展枚举（§4），其余字段复用
- `payment_record`：付款凭证 `proof_url`、金额 `amount` 复用

### 9.2 新增：`execution_task`（执行尝试明细，类比 `ai_api_cost` 独立表）
| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID | PK |

| platform | enum | taobao / jd / pdd … |

## 12. 未来展望（接口预留，去语音流兜底）

代采业务规模化 + 电商 AI 化，将改变本系统的「交互通道」。当前受控浏览器（browser transport）是初期无议价权时的 workaround；未来两种演进都已预留接口，**不对接语音流（含兜底）**。

- **方向一：规模化 → 官方 API 直连（official_api transport）**
  采购量达亿级后，可与京东 / 淘宝 / 拼多多谈判 ISV / 企业购（京东企业购、1688）直连资质，走官方下单 / 对账 API——比模拟浏览器更稳、合规、不被风控。本系统在 `PlatformAdapter` 下新增 official_api 实现，接口不变、config 切换、引擎零改动。

- **方向二：电商 AI 化 → A2A agent tool-calling（agent_tool transport）**
  若电商开放对话 / 工具调用下单接口，本系统把结构化子单翻译为它可执行的意图 + 参数（JSON / tool call），由其执行并返回**结构化回执**（订单号 / 金额）。语音只是电商侧与终端消费者交互的外壳，与本系统无关——本系统始终走结构化调用，不对接语音流。

**transport 抽象（统一接口）**：`PlatformAdapter` 底层交互通道抽象为 `browser` / `official_api` / `agent_tool` 三种 transport，统一到同一接口。未来电商开放哪种，换 transport 即可，引擎 / 状态机 / 风控全不动。

**风险（任何未来接口通用）**：对话 / API 下单不可逆、难审计 → 必须要求返回结构化回执，不依赖非结构化确认；人工闸（付款前确认）不撤。

## 附录：需求溯源
- 代采平台两大平行 AI 子系统之一 = 下单执行子系统（2026-07-31 确认）：AI + 受控浏览器替代人工在第三方电商选品 / 填单 / 付款
- 与采购需求聚合子系统平行，通过 `procurement_order` 状态衔接（其交付「已确认」子单，本系统消费），无父子 / 主从关系
- 付款账号 = 平台账号（`payer_type = platform`，非客户自付）
- 全平台覆盖：per-platform 适配器，新增平台只加一个适配器文件，引擎零改动
- 最大风险 = 平台自动化风控，须有「检测 → 熔断 → 转人工 → 同浏览器续跑 / 切备用账号」应急链路
- 复用现有状态机：不滥加字段，`status` 列扩展枚举；执行明细存独立 `execution_task` 表（类比 `ai_api_cost`）
- 混合架构：确定性 DOM 层（Playwright 主力）+ AI 视觉层（computer-use / 视觉 LLM 兜底，见《设计方案_代采平台AI方案.md》§6.13）+ 人工确认闸（合规底线）
- AI 内容归口（2026-07-31 确认）：本子系统的 AI 相关描述抽出到平台**总体 AI 方案**文档，作为其「应用场景二：直接下单」；本文档只留架构定位与指针
- 收货单位 = 客户，禁止合并（沿用主文档 §4.3）
- 不进入执行子系统：`business_type ∈ {代付款, 代询价比价}`
- 架构骨架：`execution/adapters/{taobao,jd,pdd}.py` + `execution/engine.py`
- 未来演进（官方 API 直连 / A2A agent tool-calling，预留接口、去语音流兜底）见 §12
